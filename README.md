# Literary Worx

The Literary Worx website: AI, software and cloud engineering for U.S. businesses. Built with Next.js (App Router), React, Tailwind CSS v4, TypeScript, and scroll-driven 3D scenes made with three.js, GSAP and Lenis. Every 3D object is built in code: there are no model files.

## Run it

```bash
npm ci --ignore-scripts     # or: npm install
npm run dev                 # http://localhost:3000
npm run typecheck
npm run build && npm run start
```

Node 20.9 or newer. The build needs no network access: the typeface is in the repository.

**To see the 3D scenes, use the production build (`npm run build && npm run start`).** `npm run dev` compiles each piece on first use, which can take longer than the page's safety timer allows, and the page then falls back to its static layout.

## Project pages

Each of the twelve projects in `lib/projects.ts` has a page at `/work/<slug>` (`components/ProjectPage.tsx`, served by `app/work/[slug]/page.tsx` next to the case studies): the kind of product, its tags, an overview, the challenge and the solution where they are published, features, further sections (SIQETRA's product tour, governance and delivery), a gallery of its screens and three other projects. The words are what the team has published about each project, kept to the facts (no calls to action, no other company's name, no contact details); a part that was never published is left out rather than made up. The pictures are in `public/projects/<slug>/<n>.webp` (the first is the cover); the case studies' galleries are in `public/cases/<slug>/`. The assistant is given every project in full (`lib/chat/knowledge.ts`), so it answers from the same words and links to the right page; a short list of names (`lib/project-index.ts`) is all the page-by-page question above its button needs.

## The scroll-driven 3D scenes

Every beat of a pinned section has its own object, and every object is something real that belongs to what the copy beside it says: no abstract shapes. Each is a **model** in `motion/models/`, built in code (no model files), with our own projects on its screens and pages. They stand in one plain photo studio (a glossy white floor, three soft lights, soft shadows), and each does one piece of work as the page scrolls. A screen keeps one picture: what you see changes only when the copy moves on to the next object (the two exceptions are the change the object is about: a wireframe filling in to the finished design, an invite turning into a call):

`motion/scenes/deck.ts` is the sequence nearly every scene uses: a list of objects (`data.items`) with the points in the scroll where each takes over (`data.at`), one at a time, the camera moving on to the next as the copy moves on; each object works through its own beat (`model.set(a, l, p)`: `a` how built it is, `l` how much it is running, `p` its own share of the scroll). The first object is built before the first frame; the others are built in idle moments in the background, each with its shaders compiled before it is needed. `motion/scenes/system.ts` shows one object for a whole section (the book of case studies on `/work`) and frames the box the model says it fills. The shared parts are `motion/models/glow.ts` (soft floor shadows and the nine service icons), `motion/models/real.ts` (materials, rounded boxes, turned parts, tubes, stands, the screen cross-fade, a keyboard) and `motion/stage.ts` (the studio under every scene: a floor that mirrors the model and fades with distance, and three soft lights). Soft floor shadows sit on a separate layer so they stay out of the mirror, and `motion/models/fit.ts` leaves them out when it frames a model by measuring what it really fills in the states it passes through. `motion/devices.ts` holds the laptop, tablet, phone and monitor the models put our screens on.

- **One renderer for the whole site.** `motion/gl.ts` creates one WebGL renderer, one canvas and one studio-lighting environment; `motion/mountStage.ts` moves the canvas into whichever scene's stage is on screen. So the browser holds one graphics context however many scenes a page has (checked by the verify script: never zero, never two). `motion/kit.ts` holds the low-level helpers (rounded shapes, picture loading, canvas textures, soft blobs) and `motion/engine.ts` the stage (camera, light, projection). `motion/models/parts.ts` has the drawing helpers the models are made from and `motion/screens.ts` turns a project picture into a screen texture.
- **Everything is a pure function of the scroll progress `p`**, so scrubbing forwards and backwards is exact. Randomness is seeded (`motion/models/env.ts`), so a scene is the same on every visit.
- **Pages with a scene.** `components/Xp.tsx` is a tall section with a sticky stage (no GSAP pin); one ScrollTrigger with `scrub: 0.6` (`motion/gsap.ts`) feeds `setProgress(p)`, so the picture keeps up with the hand, and the page scrolls at its normal speed inside a scene too (the wheel is never slowed). The one runway left is short on purpose (400vh for the six case studies; the other scenes play by themselves, see below); the home page shows its services as a plain grid instead of a second pinned section. The copy of each beat fades in and out beside the picture (`Phase`), and the pointer tilts the camera a few degrees on desktop. Each beat of the copy brings its own object; nothing is labelled with floating tags. Inner pages use `components/SceneHero.tsx` (the headline, two chapters and a closing call to action); the decks are `components/ServicesDeck.tsx`.
- **The layout adapts.** The copy is on the left; the scene takes the room to its right, below the floating header (`layout({ left, right, top, bottom })`); the camera distance is fitted to that room, so the picture is as large as it can be at 1024, 1280x640, 1440 and 2560 px. On a very wide screen everything stays within 1680 px. The verify script checks the picture never runs over the copy or the header.
- **Motion is opt-in.** A tiny script in `<head>` (`motion/head.ts`) sets `html.motion` only on wide screens (64rem and up) when the visitor has not asked for reduced motion, is not saving data or on 2G, and is not on a device with 2 GB of memory or less. It removes the class again after 8 seconds if the engine has not started. Everything that is hidden until animated lives under `html.motion:not(.motion-ready)`.
- **Phones, tablets and reduced motion** get plain markup and a real still picture of the home scene (`public/scene/system-ring.webp` and `system-dash.webp`, about 40 kB each at phone size, rendered from the scene itself on its own light ground by `scripts/make-posters.mjs`), plus light CSS animation. The home page's services grid is the same everywhere: nine stills of the services' objects (`public/scene/services/<slug>.webp`, 720x540, 7 to 17 kB each, lazy), rendered by the same script from the `/services` deck. Their addresses carry `?v=` (`STILL_VERSION` in `lib/scenes.ts`): raise it whenever the stills are rendered again, or browsers keep showing the old pictures for a day. A deck gives way to the plain card list; an inner page's scene gives way to its headline block. They download no three.js, GSAP, Lenis or scene runtime (checked by the verify script). If WebGL is missing, each scene steps aside the same way, at once, before anything is built.
- **The home hero is live on phones and tablets too** (`html.live3d`, set by `motion/head.ts`, the home page only, under 64rem, not under reduced motion, Save-Data, 2G, 2 GB of memory or less, or fewer than 4 cores; removed again after 10 seconds if the scene has neither started nor failed). The scene draws without GSAP or Lenis (only `mountStage` for a story that plays by itself) and starts after the page has loaded, when the browser is idle; its objects are the lighter versions. The layout is blocks (`app/styles/xp.css`, the end): the picture first under the header, the beat bars, then the words (every beat in one grid cell, so nothing below moves); the still picture shows until the scene is ready, and a failed scene keeps the static block. `/?3d=off` shows the plain page to compare. Every other page stays plain on a phone.
- **Lazy loading.** `motion/gsap.ts` imports GSAP only where `html.motion` is set; `motion/mountStage.ts`, each scene and each model are separate chunks fetched in an idle moment, about a screen and a half before the scene is reached (a service page fetches only its own model). A scene that is on screen when the page opens starts only after the first paint, so the headline is never held back by the 3D. A scene builds in steps with a pause between them (and a pause after every picture it draws), so scrolling is never blocked by the whole build, compiles its shaders before the first frame, and draws only while its section is on screen and the scroll has moved.
- **Drawing quality adapts.** The picture is drawn at the screen's pixel ratio (at most 1.75). If the graphics card cannot keep up while scrolling (ten frames in a row slower than about 28 a second) it steps down a quarter at a time, to 1.
- **Declarative layer** (`motion/MotionEngine.tsx`): `data-reveal`, `data-stagger`, `data-wipe`, `data-parallax`, `data-split`.
- **The home hero, the services page, each service page, the audit page and the about page play by themselves.** They are the scenes not tied to the scroll (`auto` on `components/Xp.tsx`, driven by `motion/autoplay.ts`; `/services` has ten beats, an introduction and the nine services, `SERVICES_AT` in `lib/scenes.ts`, each a second longer than elsewhere: `SERVICES_BEAT_MS` in `motion/timing.ts`; the others have four, `PAGE_AT`): one screen tall, so scrolling goes straight on to the next section, while a clock moves the camera through its objects, 4.5 s a beat, the first 3 s (`motion/timing.ts`), and the words change with them; after the last object the camera comes round to the first again (`loop` in `scenes/deck.ts`), and the join is pixel-exact. One bar per beat (click to jump) sits at the bottom left. It pauses while the pointer is on the words, while keyboard focus is on a button in them (that beat comes into view), while the hero is off screen or the tab is hidden, and it waits until all four objects are built (each is drawn once out of sight first, so no object's first appearance stalls a camera move). It draws every frame while the camera moves and every other frame while an object works through its beat. Phones, reduced motion and no WebGL keep the same static block as before.
- **Developer switches.** `?beat=2000` (on the home page or any page that plays by itself) shortens the beats (in ms) to watch a whole loop quickly; `/?stats` makes the page print what the 3D scene costs (read `window.__lw3d()` after scrolling); `/?still` switches off the pointer, the adaptive quality and the hero's clock so the stills are exact (`window.__lwSeek(p)` then draws the hero at progress `p`). Run `node scripts/make-posters.mjs http://127.0.0.1:3000` against a running production build to refresh the stills whenever the home story or a service's objects change (it renders the home stills and the nine service pictures), then `node scripts/make-brand-assets.mjs`.
- **Light scenes only.** Every runway is light (`xp xp-light`): a pale ground in CSS and, in the scene, the dressing from `motion/stage.ts`. There is no dark scene and no `tone` option. A sequence keeps one floor under whichever object is in front and fades its mirror while the camera travels between two.
- **Adding a model:** write `motion/models/<name>.ts` (copy a small one such as `report.ts`), register it under its name in `modelLoaders` in `motion/models/env.ts`, and put it in a sequence in `lib/scenes.ts` (`SERVICE_MODELS` for a service, `STORY` for the home page, `pageScene` for the audit and about pages), with its description for screen readers.

## Speed

Measured with `node scripts/perf-report.mjs` (headless Chrome on a laptop; the phone profile is slow 4G and a 4x slower processor), production build. See the report for current numbers; the design rules that keep it small and quick are:

no GSAP or Lenis on phones, and three.js only for the home hero (after the page has loaded, never on another page; `/?3d=off` keeps the plain page); on a fresh visit on a phone or tablet each section below the first screen is laid out only when it comes near the screen (`html.lazy`, set in `motion/head.ts`, `content-visibility: auto` in `app/styles/site.css`), and the class comes off before any jump to a place on the page (a link with a #, Back, Forward, a reload), so links always land right; the scenes load only where motion is on, never before the page is usable; one 27 kB variable font; hand-written CSS; no third-party requests (verified), except the Google Map on the contact page, which loads lazily when it is scrolled to; pictures with fixed sizes and `srcset` (the first-frame still is lazy, so a phone never fetches it); the home link is not prefetched, so no other page downloads the hero picture; static pages everywhere except the inquiry API; no backdrop blur on phones; one WebGL context shared by every scene. Response headers (`next.config.ts`): `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, `X-Frame-Options`, HSTS, and a day of caching for the stills and brand files. ScrollTrigger keeps its own 60 Hz timer running while it is loaded (about 0.2% of one processor); that is how the library works.

Honest limits: the numbers come from one laptop and a software renderer for the 3D (a "blocking time" for a desktop page that the report shows is the software renderer at work, not a real graphics card: it compiles the shaders on the main thread, which can hold a page for many seconds). The phone numbers swing a lot from run to run on the same build (a first paint of 1.6 to 3.9 s for the home page), so compare two builds side by side, not against an old report. On the phone profile the first paint waits for one large first layout of the whole page; laying out the lower sections lazily shortens it. Applied naively it made in-page links land short (the browser jumps using estimated heights for sections it has not drawn yet), which is why the lazy class is taken off before every jump; the verify script checks a link, and Back and reload were checked by hand. Check on a real machine and with PageSpeed Insights once deployed.

## Inquiry form

`/contact` posts to `/api/inquiry`, which validates the fields, **saves the message in the admin inbox** (see "Admin area" below) and then sends two emails through SendGrid's Mail Send API (no SDK, one `fetch`). A message counts as received once the inbox or the team email has it, so a SendGrid outage no longer loses one (the inbox marks it "team e-mail did not go out"); with only one of the two set up, that one is used; with neither the API answers 503.

- **To the team** (`CONTACT_TO_EMAIL`, a comma-separated list is fine): the interest, name, email, company, time received (San Antonio time) and the message, with a Reply button. Its reply-to is the visitor, so replying answers them directly.
- **To the visitor**: a short confirmation with what happens next. It repeats nothing they typed except their first name, so the form cannot be used to send a stranger a message of someone else's choosing. If it fails, the visitor still sees success, since their message has reached us. Turn it off with `CONTACT_SEND_CONFIRMATION=false`.

The templates are in `lib/mail/inquiry-email.ts`: table layout with inline styles (what email clients render reliably), an HTML and a plain-text part each, every visitor field escaped, and no images, remote fonts or tracking (click and open tracking are switched off in the request).

Setup in SendGrid: create an API key with only the **Mail Send** permission, and verify the sending address (Single Sender Verification) or, better, authenticate the domain (Settings â†’ Sender Authentication, the DNS records SendGrid gives you) so the emails pass SPF and DKIM. Then copy `.env.example` to `.env.local` (or set the variables on the hosting platform) and fill in `SENDGRID_API_KEY`, `CONTACT_TO_EMAIL`, `CONTACT_FROM_EMAIL` (the verified address) and `NEXT_PUBLIC_SITE_URL`; `CONTACT_FROM_NAME`, `CONTACT_REPLY_EMAIL` and `SENDGRID_API_BASE` (`https://api.eu.sendgrid.com` for an EU account) are optional. Without the required ones the API answers 503 and says the inbox is not configured. A refusal from SendGrid is logged on the server with its reason (never the key or the message).

The API also limits one address to 8 requests in ten minutes (in memory: a real limit on a long-running server; on a serverless host each instance counts for itself, so add the platform's rate limiting too). Set real keys on the hosting platform, not on a shared or untrusted machine.

## Website assistant

The round button in the corner of every page opens the assistant (`components/chat/`). It answers questions about the services, case studies, prices and the AI audit from the site's own content (`lib/chat/knowledge.ts` builds it from `lib/content.ts`, `lib/services.ts` and `lib/service-pages.ts`, so a change to the site changes what it knows), streams the answer word by word, suggests follow-up questions, and offers "Book a free AI audit" or a short "Ask us to contact you" form, which sends an inquiry through `/api/inquiry` with the conversation attached. The panel's code loads only when a visitor reaches for the button, so pages are no heavier. The conversation is kept in the browser tab (sessionStorage) and nowhere else.

`/api/chat` calls Claude (Anthropic's Messages API through the official `@anthropic-ai/sdk`, model `claude-opus-5-5` at low effort for a fast first word, with Anthropic's server-side fallback if a safety check declines a request). The instructions and the knowledge are one fixed block that Anthropic caches; the page the visitor is on is sent after it, so "this service" means the right one. It keeps the last 12 messages, refuses messages over 2000 characters and requests from other sites, and limits one address to 24 messages in ten minutes (in memory, like the inquiry form). Set `ANTHROPIC_API_KEY` (with a monthly spend limit in the Anthropic Console); `ANTHROPIC_MODEL` and `ANTHROPIC_MAX_TOKENS` are optional. Without the key the assistant answers with a pointer to the contact form. Above the button, a question changes with the page (`lib/chat/teasers.ts`); tapping it opens the chat and asks it, and closing it keeps it away for the visit.

## Admin area

`/admin` is a small private panel for what the website receives (`app/admin/`, `components/admin/`, `lib/admin/`, `app/api/admin/`, styles in `app/styles/admin.css`). It has its own shell and stylesheet: none of the public site's header, footer or stylesheet is drawn (the root layout is only the document; the public pages sit in the `app/(site)` group, which adds `components/SiteChrome.tsx`), it is kept out of search engines (noindex meta and header, `Disallow: /admin`, not in the sitemap) and out of frames, and nothing under it is ever cached.

- **Overview:** unread, last 7 and 30 days, all time; a 14-day column chart (hover or focus a column; "View as a table" has the numbers); what people ask about; the latest messages.
- **Inquiries:** every message from the contact form and from the assistant (with the conversation before it), newest first, with status tabs (New, Read, Replied, Archived), search, a topic filter, paging, **Export CSV** (spreadsheet formulas in a message are defused), a status for each, a private note, a "Reply by e-mail" button and delete (with a confirmation). Opening a new message marks it read.
- **Security:** what protects the area, this session, "Sign out everywhere", and the last 40 sign-ins, failed attempts and blocks (time, address, device).

### Setting it up

1. **Connect a store.** MongoDB Atlas (a free M0 cluster is enough): create the cluster, a database user (Atlas can make the password), and let the host in under Network Access (on Vercel that means `0.0.0.0/0`, since its addresses change; the user's password is what protects the data). Copy the connection string (Connect, Drivers), put the password in it, and set it as `MONGODB_URI` on the host (Vercel: Project Settings, Environment Variables). `MONGODB_DB` names the database (default `literaryworx`). Redis works too (`KV_REST_API_URL` and `KV_REST_API_TOKEN`, which Vercel's Storage, Redis adds by itself). Locally, with neither, `.data/store.json` is used (git-ignored; `LW_STORE=file` does the same on a server that keeps its disk).
2. **Redeploy, then open `/admin`.** The first visit shows "Make the admin account": your e-mail address and a password (12+ characters; "Make a strong one for me" fills in a random one to save in a password manager). The account goes into the database (the password only as a scrypt hash), you are signed in, and the form closes for good. Do this right away: until it is done, anyone who opens `/admin` could make the account. Set `ADMIN_SETUP_KEY` to a word only you know and the form asks for it too, which closes that gap.
3. Optional: two-step sign-in. `npm run admin:setup` prints a key for an authenticator app (Google or Microsoft Authenticator, 1Password, Authy: "Add account", "Enter a setup key"); set it as `ADMIN_TOTP_SECRET`.

The account can instead come from the host's settings: `npm run admin:setup` asks for an e-mail address and a password (or `-- --generate` makes one) and prints `ADMIN_EMAIL`, `ADMIN_PASSWORD_HASH`, `ADMIN_SESSION_SECRET` (and the 2FA key; `-- --no-2fa` leaves it out, `-- --write .env.local` writes a local file). Settings win over a stored account, and the first-run form is not offered.

In MongoDB the messages are in the `inquiries` collection (one document each: name, email, company, interest, message, status, note...), and the account, counters and sign-in log in `kv`. Messages sent before a store was connected are not in the inbox (they only went by e-mail). Nothing links to `/admin` from the public site.

### How sign-in is protected

- **Password:** only a scrypt hash (N=65536, r=8, a random salt per hash) is stored (in the database, or in the host's settings), never the password. A wrong e-mail address costs the same time as a wrong password (a decoy hash is checked), and every failure gets the same sentence, so it does not say which part was wrong.
- **Two-step:** a six-digit time-based code (RFC 6238, checked against the standard's test vectors), one step of clock slack, and a code works **once** (the step is remembered for two minutes). Lost the phone? Make a new key with `admin:setup` and replace `ADMIN_TOTP_SECRET` and `ADMIN_PASSWORD_HASH`.
- **Limits:** 8 attempts in 15 minutes from one address and 30 an hour on the account, counted in the store before any work is done (so a flood of parallel requests cannot get past it) and shared by every server instance. Over the limit the answer is 429 with `Retry-After`, even for the right password.
- **Session:** a signed cookie (HMAC-SHA256) that is `HttpOnly`, `SameSite=Strict`, `Secure` with the `__Host-` prefix in production, valid 8 hours (`ADMIN_SESSION_HOURS`). Signing out ends that session on the server (not only in the browser), and "Sign out everywhere" ends every session made so far. A made-up, expired, re-signed or over-long token is refused.
- **Same-site only:** every change (sign-in, status, note, delete, sign-out) must carry an `Origin` header of the site's own host, on top of `SameSite=Strict`. Visitors' text is rendered as text (never as markup).
- **Record:** sign-ins, failures (with the reason, shown only to you), blocks and sign-outs go to a log of the last 200 events.
- **Address:** the visitor's address is taken from `x-vercel-forwarded-for` (set by Vercel and not forgeable there), then `x-real-ip`, then `x-forwarded-for`. Behind another proxy, make sure it overwrites those headers; the account-wide limit holds either way.

`node scripts/verify-admin.mjs` checks all of this against a running server over HTTP (`ADMIN_EMAIL`, `ADMIN_PASSWORD`, optionally `ADMIN_TOTP_SECRET` and `ADMIN_SESSION_SECRET`; start with an empty store, since it adds messages and uses up attempts). `node scripts/verify-admin-setup.mjs` checks the first-run form (`SETUP_EMAIL`, `SETUP_PASSWORD`, optionally `SETUP_KEY`; a server with a store, no account yet and no `ADMIN_EMAIL`, `ADMIN_PASSWORD_HASH` or `ADMIN_SESSION_SECRET`): weak and mismatched passwords, a wrong setup key and other sites are refused, six simultaneous requests make exactly one account, and the form is closed afterwards. Run it first, then `verify-admin.mjs` with the same e-mail and password. Both work on any store; use a scratch database (`MONGODB_DB`) when they run against Atlas.

## Hosting

The site is a standard Next.js app (`npm run build`, then `npm run start`), with no host-specific package. It is set up for three hosts; on all of them the settings are the ones in `.env.example` (put them under the host's environment variables, never in git: `.env` and every `.env.*` file except the example are git-ignored), and `NEXT_PUBLIC_SITE_URL` must be the site's own address.

| Host | What to do |
| --- | --- |
| **Vercel** | Import the repository; set the variables; deploy. Nothing else (the visitor's address and country come from Vercel's own headers). |
| **Netlify** | Import the repository. Next.js 16 needs no plugin (Netlify's OpenNext adapter is used automatically); `netlify.toml` only pins Node 22. Set the variables under Site configuration, Environment variables. The visitor's address comes from `x-nf-client-connection-ip` by itself. |
| **AWS Amplify Hosting** | Import the repository (Amplify picks the `WEB_COMPUTE` platform for a Next.js app). `amplify.yml` installs with `npm ci`, writes the variables the site reads into `.env.production` (Amplify gives the server runtime no console variables otherwise; the file ends up in the build, so give the database user only this site's database) and builds. Set `TRUSTED_IP_HEADER=cloudfront-viewer-address` (and allow that header in the distribution's origin request policy) so the sign-in limits see the visitor's address. |
| **Any Node server** | `npm ci && npm run build && npm run start` behind HTTPS. Name the header your proxy sets for the visitor's address in `TRUSTED_IP_HEADER` (Cloudflare: `cf-connecting-ip`). |

Every host needs the same two things for the admin inbox: `MONGODB_URI` (Atlas, Network Access open to the host: `0.0.0.0/0` on a serverless host, since its addresses change) and a first visit to `/admin` to make the account. The request helpers (`lib/request.ts`) read the visitor's address from the host's own header, accept a request as "from this site" when its `Origin` matches the `Host` or `NEXT_PUBLIC_SITE_URL`, and are used by the inquiry form, the assistant and the admin area alike. Two things to check on a host other than Vercel: the function time limit (the assistant streams an answer for up to about 30 seconds), and that the host serves HTTPS (the admin cookie is `Secure`).
